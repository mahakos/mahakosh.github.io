1. Summary

The testbench is in good shape for a v0.1. It has a real reference model and scoreboard, so it checks data instead of only checking that the simulation finished. Every one of five deliberately planted RTL bugs made at least one test fail.

But the 100% coverage number flatters it. Coverage closes in 100 to 200 random transactions across ten seeds, which tells us the coverage model is too small to be a good measure of "done". Three of the five planted bugs were caught only by random traffic, one of them partly by luck, and one was caught by a crash rather than a clear error message. The fixes are small, and they are listed in section 5.

3. Does the testbench catch real bugs?

A passing test only matters if it would fail on a broken design. So we planted five bugs in the RTL, one at a time, and ran the full regression with seed 1234. This is called mutation testing, and it is the quickest honest way to measure a testbench.

The directed tests alone caught only two of the five. That is normal, and it is why random stimulus with a scoreboard matters. It is also why the next findings focus on making the random side stronger.

4. Findings

Medium F1. The monitor crashes on unknown (X) values

When the design drove an undefined value on PRDATA, the monitor's integer conversion raised a Python exception. The test failed, which is good, but the log points at the testbench instead of the design. On a real project this costs an engineer an hour of confusion each time.

Fix: check is_resolvable before converting, and report X on PRDATA at addr=… as a scoreboard error.

Medium F2. Reset values are not checked on purpose

No test reads registers straight after reset before writing them. The reset bug was caught only because a random read happened to hit an unwritten register. With a different seed or a larger register file, it could slip through.

Fix: a directed reset-value test, and a coverage bin for "read before first write" on every register.

Medium F3. 100% coverage is too easy to reach

Coverage closes in 100 to 200 transactions on all ten seeds we tried (1 to 10). The model counts each feature on its own, so it never asks whether every strobe pattern was used on every register, or whether a partial write was followed by a read that would show the result.

Fix: add crosses (register × strobe pattern, write-then-read on the same register, back-to-back accesses) and check for closure after every transaction instead of every 100.

Low F4. No wait states and no protocol assertions

The design ties PREADY high, so the driver's wait-state path has never run. There are also no assertions on APB rules such as "PADDR stays stable while PSEL is high" or "PENABLE only rises one cycle after PSEL".

Fix: a version of the design with random wait states, and a small set of SVA or cocotb protocol checks, ideally also proven with SymbiYosys.

5. What we'd do next

  1. Fix F1 and F2 first. Both are under a day of work and make every future failure easier to debug.
  2. Rebuild the coverage model with crosses (F3) and re-run the five planted bugs to confirm they are now caught on purpose, not by chance.
  3. Add wait states and protocol assertions (F4), then a formal run on the handshake.
